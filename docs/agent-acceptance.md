# Agent acceptance: the final development gate

Use this procedure before declaring a user-facing feature complete. Unit, architecture, specification, lint and format checks establish implementation correctness within their tested scope; fresh-agent acceptance establishes whether an agent can achieve the user's declared task through the shipped CLI and skill. Both are required for a feature verdict. This document is developer orchestration guidance, not an additional operator skill.

The development agent owns scope, setup, evidence review and the final verdict. Fresh operator agents know only their task brief, the candidate executable, the shipped `skills/audio-cli/SKILL.md` and its references, public CLI help/results, and their own artifacts. Do not give them this document, repository source, developer instructions, tests, implementation plans, issue/PR discussions, historical results or another operator's conversation. Do not fork the development conversation. Keep the shipped skill outside `.agents/skills/`; do not install it into the development workspace to conduct acceptance.

## Declare the task before testing

Record the candidate commit, executable path/version, skill path, fixture identity, full-source or range scope, required capabilities, required deliverables, and the checks that decide each requirement. Bind the executable to the candidate: retain the build/install command and artifact digest, or verify that the editable installation resolves to that exact checkout and record any uncommitted diff. A matching version string or executable filename is insufficient. Hash the skill entry point and every shipped reference/support file; retain that exact snapshot with its candidate origin. Freeze the candidate during testing and verify identity again afterward. Distinguish a user requirement from an optional diagnostic. An added timing/export check must have its own verdict; its failure must not be reported as a total ASR or diarization failure. Conversely, a required capability cannot become optional after it fails. Declare any accepted fixture-specific limits with the user's prior decision and exact artifact/configuration identity.

Use the full matrix below for changes to transcription, enhancement, shared command behavior, package readiness or the shipped skill. Add a task-specific case for the new feature and for any newly fixed acceptance defect; repeated media cases alone do not prove that a new command or flag works. For a narrower change, record which cases are affected and why the others are not required. Documentation-only changes need link/content verification rather than another model run, unless the changed document is operator guidance whose usability is the feature under test. This scope decision is recorded before execution.

## Prepare an isolated, reviewable run

1. Inventory the main checkout, candidate worktree, active work and existing evidence before cleanup. Remove only completed-task disposable files; preserve private source media, accepted baselines and unrelated work. Do not overwrite an earlier test directory or remove evidence merely to make the workspace look clean.
2. Run the implementation checks appropriate to the change and `uv run --extra dev pre-commit run --all-files`. Record skips and failures with their scope. Resolve the actual current test path from [the test layout](testing.md); do not treat an unexecuted check as passed.
3. Create `tests/artifacts/acceptance/<date>-<candidate>/` with a manifest and one directory per operator case. Research runs may instead use `model_tests/benchmark_runs/`. Record original input SHA256 and byte size before and after execution. Keep raw private recordings, transcripts and logs untracked; publish a compact result under `model_tests/benchmark/results/YYYY-MM-DD-<topic>.json`.
4. Prepare a command recorder before the first operator action. Record exact executable/arguments, working directory, start/end time, exit status, and raw stdout/stderr for every CLI invocation. Record non-audio setup and review commands too, or explicitly mark their journal incomplete. Do not reconstruct missing timestamps or infer successful execution from filenames.
5. Start separate agents with fresh contexts and an external working directory outside repository instruction discovery, separate from repository evidence storage. Supply absolute paths to the candidate, skill snapshot and output directory; do not ask operators to infer the candidate from a shell's current `audio`. Do not launch the operator from a repository artifact directory whose ancestors contain developer instructions. If the agent system cannot isolate the context, report the acceptance setup blocked rather than label an inherited development context fresh.
6. Use a shared execution lock for full inspect/enhance/transcribe/model-provision operations when parallel models would contend for memory. Hold it for the CLI child's lifetime. Help, plans, saved-result exports and offline report reads can proceed independently. Record lock waiting separately from execution time; this acceptance run is not a controlled performance benchmark.

The fixture inputs are optional private files under `tests/artifacts/media/`. If a fixture is missing, mark its case blocked and request the source through the normal user workflow. Do not download a substitute, silently use a shorter clip or declare a skipped fixture passed. Package readiness and provisioning must use the CLI's explicit `doctor`/`packages` lifecycle; no manual environments, weights, lock edits or provider setup. Provisioning explicitly required by a ready-state plan is setup, not permission to retry an unsuccessful model run.

## Operator brief template

Give each operator the following brief with placeholders resolved. Include only its matrix row and task-specific requirements, not the development gate or other cases' results.

```text
Task: <user-facing operation and required deliverables>.
Candidate executable: <absolute path>.
Shipped skill: <absolute path>/skills/audio-cli/SKILL.md.
Original input: <absolute path>. Evidence output: <new absolute case directory>.
Operator cwd: <new external absolute directory with no repository instructions>.
Required scope/capabilities: <full source or explicit range, stack, wants, profile>.
Optional diagnostics: <explicitly optional checks, if any>.
Learn usage only from this brief, that skill/references and public CLI help/results. Do not inspect repository implementation, developer docs, tests, issues, old results or other agents.
All audio/model processing, inspection, transcription, enhancement, export and provisioning must use the supplied CLI. Non-audio filesystem, command logging and JSON inspection tools are allowed. Do not invoke FFmpeg, an audio library, a provider SDK or another processor directly.
Preserve the original and any canonical JSON. When transcription is required, transcribe original media before enhancement; do not add ASR to an enhancement-only task. No filler/editorial cuts, manual text cleanup, invented timing, fallback backend or reduced request.
Use the provided recorder and shared lock. Save every command's raw streams and exit status, all canonical results, native readable exports, reports and available diagnostic logs.
On the first unexpected failure, unsatisfactory required capability or required-output refusal, preserve evidence and stop the dependent workflow. Do not retry, repair, drop flags, switch stacks or use an alternative. Report the exact blocker and leave unattempted steps explicit. You may finish non-audio inspection/reporting of already saved evidence. Do not make further CLI calls after that stopping condition. Independently predeclared cases may continue in their own agents.
Report requirement-by-requirement PASS/FAIL/BLOCKED, actual artifacts and their limits, and concrete CLI/skill positives and improvement suggestions. Do not score accuracy or listening quality without a reference or human judgment.
```

Deliberate negative tests are an exception to the unexpected-failure stop rule only when declared in advance: a specified refusal is their expected success condition. Do not retrofit that label onto an unexpected refusal. Likewise, a valid partial result or abstention can satisfy a test of honest partial-result handling while failing a task that requires complete timing. Keep the two verdicts separate.

The dependency sequence matters. In D2, incomplete required word timing stops subsequent CLI steps even if ASR and diarization produced useful results. If the task only requires untimed speaker attribution, declare timing diagnostic rather than required before execution; its outcome then has no authority to fail that narrower user requirement. Missing attribution in a scope is reported even when all emitted text has a speaker label. Anonymous speaker IDs are not names, and model-to-model label equality establishes no shared identity.

## Evidence checks and verdict

Read the canonical artifact, not an agent summary, to verify what a backend supplied. Inspect `provenance.outcomes`, `abstentions`, `complete`, recorded range/coverage, emitted segments, words and turns. A capability declaration or successful plan is not a produced capability. `complete: true` is not a guarantee of verbatim text, exhaustive speech coverage or complete timing. Distinguish absent `words` from a supplied empty array; do not turn missing measurements into zeroes or nulls.

For timing, verify the recorded bounds against the source timeline and the documented export requirements. Keep zero-duration, missing and rejected timing visible. Never use source length, a diarizer turn, processing-unit bounds or another model's timing to repair a gap. A native exporter can detect missing timing from one saved result without a reference transcript. It cannot establish whether recognized words, speaker labels or boundaries are correct simply because they are structurally valid.

For enhancement, distinguish processing applied from effectiveness measured. Inspect actual encoded-output metrics separately from predictions and intermediate stages, plus nested evidence limits even when `unresolved` is empty. Compare fixed original regions separately from fresh output detection and its speech reference. Apply only declared thresholds and explicitly accepted fixture-specific limits; do not invent a quality score. A decoded-duration check does not prove exact content alignment or A/V sync. Recognition accuracy, dialect/filler recall, speaker correctness and perceptual improvement need user judgment or an appropriate annotated/clean reference.

| Requirement status | Meaning and effect on the feature gate |
| --- | --- |
| PASS | The requested behavior and its declared evidence criteria are met; required outputs exist and validate. A negative test passes only with its predeclared refusal. |
| FAIL | The candidate was exercised and a required behavior or deliverable was not achieved. Record the responsible component; correct refusal behavior may pass its safety check while the requested delivery fails. |
| BLOCKED | A prerequisite or required judgment is unavailable, or the stop rule leaves a dependent step unattempted. Name the blocker; do not imply that the unattempted command failed. |
| NOT REQUIRED | Scope excluded this check before execution. Preserve optional observations but do not let them silently redefine the feature. |

The final feature verdict is **PASS only when every required implementation and operator requirement passes**, with any required human judgment recorded. Any failed requirement makes it FAIL. If no requirement failed but evidence is blocked, report BLOCKED, which is not release acceptance. “Partial success” may describe useful delivered components, but is not a passing final gate. Existing known limitations must remain explicit; neither their age nor an unrelated PR's green tests waives them. A narrow feature may pass its own gate while the full matrix remains blocked or failed elsewhere, provided that scope was declared in advance and the broader status is disclosed.

Prior human acceptance can be reused only for the unchanged scope it actually covered and with identity evidence. Byte-identical rendered media can retain that exact render's recorded listening decision. Exact canonical segment/word/turn equality can retain a previously recorded judgment of those fields; run-specific metadata need not match. Neither equality nor another model's output creates ground truth. New or changed Qwen text and attribution still need review. Do not infer a general waiver from prior acceptance of the demo's recorded loudness-range limit.

## Close the development loop

The development agent reviews every required artifact and refusal, audits source identity and the operator protocol, and writes one report with a requirement/status table, links to canonical/readable transcripts and playable outputs, exact blocker evidence, human-judgment state, command/log inventory and concrete CLI/skill feedback. Record missing logs or context contamination as harness limitations, separately from product failures. Add a compact tracked JSON result naming fixture hashes, configuration, candidate, outcomes, unresolved goals, raw artifact locations and the final scoped verdict. Do not upload private media or full transcripts as public issue evidence.

Triage feedback against the current source/help and existing issues. Separate confirmed defects, demonstrated usability gaps, optional ideas, already shipped behavior and out-of-scope work. Open focused issues with evidence, acceptance criteria and ownership boundaries only for genuine gaps. The testing operators do not patch the CLI. Fixes happen in development, then affected cases are repeated by new fresh-context operators against a new candidate; retain the original failure record. Obtain independent evidence review and resolve material findings before declaring the feature passed. Permission to test or submit a PR is not permission to merge it.
